AI job-fit scoring with Zapier

Build a scheduled Zap that runs one bounded candidate search, filters validated fit rows, and updates or creates a Google Sheets row by candidate-specific matchKey.

Not an importable ZapBuild 0.1.22Five-result starter
Open the editor recipe ↗Review the scorer

Availability boundary

Zapier does not provide a portable workflow-import file for this maintained recipe. The repository contains a human-readable editor specification. It is not a published Zap, does not include credentials, has not proved an authenticated editor build, and is not evidence that a named Google Sheet received a row.

Build the Zap

  1. Add Schedule by Zapier → Every Day, but keep the Zap off during setup.
  2. Add Apify → Run Actor for nomad-agent/ai-job-fit-scorer. Pin build 0.1.22, use the bounded five-result input with resultMode: "shortlist" and minDeliveryScore: 2, and set maximum total charge to $0.10.
  3. Require the returned run to be terminal SUCCEEDED, exit code 0, and the exact build. If the action hides these fields, add Webhooks by Zapier requests against that exact run ID.
  4. Fetch dataset items only from that run’s default dataset ID.
  5. Continue only for nomad-ai-job-fit-v1, scoring v3, evaluationStatus: "scored", and delivery score at least 2.
  6. Look up a Google Sheets row by matchKey; update one exact match or create a new row.

Map the candidate-specific destination

Import the repository’s 21-column fit header into a disposable Sheet. Preserve matchKey, evaluationKey, candidate hashes, fit and delivery scores, recommendation, evidence summaries, source run/build, and a bounded serialized copy of the evaluation.

Do not use jobKey as the lookup key. It identifies one source posting and would allow candidate A’s evaluation to overwrite candidate B’s.

Validate before activation

  1. Inspect current nomad-ai-job-fit-run-summary-v4 from the exact run’s key-value store.
  2. Reconcile dropped, held, scored, failed, filtered, and output counts; confirm shortlist rows meet the delivery threshold and one $0.02 event exists per returned row.
  3. Prove one named row is created in a disposable Sheet.
  4. Repeat the same fixture and prove the same row is updated rather than duplicated.
  5. Use filtered, audit, and ai_failed fixtures to prove unsafe rows are blocked.
  6. Only then activate the schedule and record the run, build, destination, and verification time.

Troubleshooting

  • Build or storage fields are missing: use authenticated Webhooks steps to re-read the returned run; never substitute a latest-run lookup.
  • Duplicate candidates: inspect the lookup column and confirm it is matchKey.
  • Wrong charge: stop the Zap, confirm build 0.1.22, row status, result meter, and maximum total charge.
  • No Sheet row: distinguish a safe filtered outcome from a connection, field-mapping, or permission failure.
